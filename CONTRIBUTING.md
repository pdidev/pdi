# Contributing to PDI

Thank you for your interest in contributing to PDI!

This guide covers what you need to know to work on the PDI source distribution: how to set up a
development build, run the tests, find your way around the source tree, and submit your work.
The [Coding style](#coding-style) section at the end is the reference you will want to keep at hand
while writing code.

If you are looking for information on *using* PDI rather than developing it, see the user
documentation at https://pdi.dev

## Introduction

A few things about this repository are worth knowing before you start, because they are not what you
might expect and they shape everything else.

**This is a superbuild, not a single CMake project.**
The top-level `CMakeLists.txt` does not `add_subdirectory` the components.
Instead, each of them, the PDI library, every plugin, the examples, the test suites, is declared as
an *independent* CMake project assembled with `ExternalProject_Add`, and each is built and installed
into a staging tree that the others then find through `find_package(PDI)`.
The practical consequences are covered in [Project structure](#project-structure); the one to
remember now is that a component can also be configured and built on its own against an already
installed PDI.

**Most functionality lives in plugins.**
The PDI core deliberately knows nothing about HDF5, NetCDF, Python or MPI.
Plugins are shared libraries loaded by name at `PDI_init` according to the YAML configuration, and
they interact with the core exclusively through the public plugin API.
Adding support for a new I/O library is therefore a new plugin, not a change to the core.

**The C API is a thin shell over C++ internals.**
`include/pdi.h` is C, but the implementation behind it is C++.
The Fortran bindings are *generated* at build time from `.zpp` sources, so do not edit the generated
`.F90`; edit the `.zpp`.
The Python bindings use pybind11 and are only built when `BUILD_PYTHON` is on.

## Getting in touch

To make you known to others, please join the PDI slack channel at https://pdidev.slack.com

Bugs and feature requests are tracked at https://github.com/pdidev/pdi/issues

## Setting up a development build

The dependencies and the supported compiler versions are listed in the [source installation
documentation](pdi/docs/Source_installation.md); that page is the authoritative list and is kept up
to date as dependencies change.

Some components are git submodules, so clone recursively (or initialise them afterwards):

```bash
git clone --recurse-submodules https://github.com/pdidev/pdi.git
# or, in an existing clone:
git submodule update --init
```

`DIST_PROFILE` is the switch that distinguishes a developer build from a user build.
Setting it to `Devel` turns on `BUILD_TESTING`, `BUILD_DOCUMENTATION` and `BUILD_UNSTABLE`, and
defaults the build type to `Debug`.
`<build>` denotes your build directory throughout this guide; the examples use `.build`, but you
are free to put it wherever you like:

```bash
cmake -DDIST_PROFILE=Devel -S . -B .build
cmake --build .build -j
```

Building PDI as a static library is not supported: `BUILD_SHARED_LIBS` must stay `ON`, and the
configure step fails outright if it is not.

Anything that links PDI needs its runtime environment set up.
Use the generated `pdirun` wrapper (`<install>/bin/pdirun <command>`) or source the generated
`env.bash`.

### Keeping your working copy clean

Your `<build>` directory, your `CMakeUserPresets.json` and whatever your editor or other tools
leave behind will show up as untracked files.
Ignore them in `.git/info/exclude`, which is local to your clone, rather than in `.gitignore`:

```bash
cat >> .git/info/exclude <<'END'
/.build/
/CMakeUserPresets.json
.vscode/
END
```

`.gitignore` is committed and therefore imposed on everyone, so it *should* only list files that are
generated by a tool the project mandates, at a location that no user choice can change; the Python
bytecode it currently holds, for instance.
Anything that depends on a choice you made (which tools you use, and where you put your build
directory for example) belongs in `.git/info/exclude` instead, even when the name of the file itself
is fixed, as `CMakeUserPresets.json` is.

## Running the tests

**Run `ctest` from the top-level build directory, not from a sub-build.**
The tests themselves live in the individual component builds, but the top-level
`CTestTestfile.cmake` pulls them in through a generated `SubTests.cmake`, which is also what sets
`LD_LIBRARY_PATH` to point at the staging tree.
Running `ctest` inside a sub-build skips that setup.

```bash
ctest --test-dir .build --output-on-failure --timeout 90
ctest --test-dir .build -N                       # list the tests
ctest --test-dir .build -R '^decl_hdf5' --output-on-failure   # run a subset
```

Test names are set explicitly in each component's `tests/CMakeLists.txt`.
The C++ unit tests are GoogleTest binaries registered through `gtest_discover_tests`, so
`--gtest_filter` works when running such a binary directly.

Before submitting, check the formatting, which is the first thing CI verifies and which gates every
other job:

```bash
./bin/test_indent           # check
./bin/test_indent --apply   # reformat in place
```

`./bin/build_and_run_all_tests` reproduces a full CI run locally:

```bash
./bin/build_and_run_all_tests
```

It configures and builds the distribution from scratch, runs the whole test suite, installs it,
then configures, builds and runs `tests/cmake_tests` against that installation, so it also checks
that the installed package is usable through `find_package`.
It takes no argument and builds in a fresh `pdibuild.XXXXX` directory created in the current
directory, so it leaves your own build tree alone.
Set `TEST_DIR` to build somewhere specific, `MAKEFLAGS` to control the parallelism, and
`EXCLUDED_PDI_TESTS` to skip tests.
CI runs that same script inside the project docker images across a matrix of compilers, MPI
implementations and dependency sources, so running it before submitting is the closest you can get
to knowing CI will pass.

## Project structure

The [README](README.md) lists the directories of the distribution.
This section covers what that listing cannot: how the pieces relate.

### Components and their targets

Each component is a standalone CMake project with its own `CMakeLists.txt` that finds PDI with
`find_package(PDI)` against the staging tree.
The superbuild wraps each one in a `<NAME>_pkg` target, so a single component can be rebuilt with,
for instance:

```bash
cmake --build .build --target TRACE_PLUGIN_pkg
```

Sub-builds install into `<build>/staging` and are declared `BUILD_ALWAYS`, so they are
reconsidered on every build of the top-level project.

Dependencies are declared with `sbuild_add_dependency(<name> AUTO|SYSTEM|EMBEDDED ...)`: they are
either found on the system or built from `vendor/`.
`USE_DEFAULT` sets the global policy and `USE_<name>` overrides it for a single dependency, e.g.
`-DUSE_spdlog=EMBEDDED`.

### The core library

The C API declared in `pdi/include/pdi.h` (`PDI_init`, `share`, `access`, `release`, `reclaim`,
`event`, `expose`, `finalize`) is a thin layer over the C++ internals, of which the following are
the ones you will meet first:

* **`Context`** (`pdi/include/pdi/context.h`) is the interface plugins see: a store of named data
  descriptors, the datatype-template parsers, and the callback registry (`on_init`, `on_data`,
  `on_data_remove`, `on_event`, `on_missing_data`), each registration returning the function that
  undoes it.
* **`Ref`, `Ref_r`, `Ref_w`, `Ref_rw`**, all aliases of `Ref_any<R,W>` in
  `pdi/include/pdi/ref_any.h`, are the reference-counted, access-locked handles through which shared
  buffers reach plugins.
  The read and write permissions are part of the type.
* **Datatypes** form a tree of `Scalar`, `Array`, `Record`, `Tuple` and `Pointer` types, each built
  from a `Datatype_template`.
  A template is only fully evaluated when data is shared, because it may contain `Expression`s that
  refer to other data; sizes and selections can therefore be dynamic.

`mock_pdi/` is a header-only, no-op implementation of the same `pdi.h`, so that an application can
be built and run without PDI at all.

### API levels

There are four levels of API for PDI:

| **API level**       | **Headers**               | **Language** |
|:-------------------:|:-------------------------:|:------------:|
|  public application | include/pdi.h             | C            |
|  public application | include/pdi.F90           | Fortran      |
|  public plugin      | include/pdi/*.h           | C++          |
|  library-wide       | src/*.h                   | C++          |
|  file-local APIs    | not exposed in any header | C++          |

The first three levels are contracts with people outside the library, and breaking them is a
breaking change; the last two are internal and may be changed more freely.

### Plugins

A plugin defines a `class <name>_plugin: public PDI::Plugin` with a constructor taking
`(PDI::Logger&, PDI::Context&, PC_tree_t)` and invokes the `PDI_PLUGIN(<name>)` macro, which emits
the loader together with the optional `dependencies()` and `pretty_name()` hooks.
Plugins do their work by registering callbacks on the context from their constructor.
`pdi/docs/How_to_create_plugin.md` is the reference for writing one.

### Tests

There are several test suites, each with a different purpose:

* `pdi/tests/` and `plugins/*/tests/` are the per-component tests, including the C++ unit tests;
* `tests/api_tests/` exercise the public API against either PDI or mock PDI;
* `tests/combination_tests/` cover interactions between plugins;
* `tests/cmake_tests/` verify that a real installation can be consumed through `find_package`;
* `example/` doubles as an integration test suite.

## Making a change

### Changelog

Every user-visible change is recorded in [CHANGELOG.md](CHANGELOG.md) under the `[Unreleased]`
heading.
The project follows [Keep a Changelog](https://keepachangelog.com/en/1.0.0/) and [Semantic
Versioning](https://semver.org/spec/v2.0.0.html).

`[Unreleased]` describes the difference a user of the *last released* version would see when
upgrading to the next one.
It is not a log of commits, nor of the work that went into a branch.
Four rules follow from that:

* **No entry for a bug that never shipped.**
  If a regression is introduced and fixed again before it reaches a release, across commits of the
  same branch, for instance, nothing outside that branch ever observed it, so it gets no entry.
  Judge every change against the latest release, not against the branch.
* **Pick the section by who is affected, not by which code you touched.**
  *For users* is the application or library consumer: someone writing YAML configuration or calling
  `pdi.h` / `pdi.F90`.
  *For plugin developers* is whoever writes a `PDI::Plugin` subclass or otherwise codes against the
  public plugin API.
  A change confined to the library-wide or file-local levels of the [API levels](#api-levels) table
  is invisible to both and gets no entry, unless it changes observable behaviour.
* **State the observable change, not the reasoning or the implementation.**
  Say what a reader must now do differently, or what now behaves differently.
  Leave out why the design was chosen, and leave out internal class or member names that are not
  part of the public API.
  For example, "Merged `Callbacks` into `Global_context` and renamed the callback functions" states
  an API change, it belong in the CHANGELOG.
  On the other hand, "declared `m_loaded_plugin` before `m_plugin_logger` to handle destruction
  order correctly" is an implementation detail that belongs in the commit message.
* **Link the issue the change resolves**, as `[#NNN](https://github.com/pdidev/pdi/issues/NNN)`,
  issues, never pull requests.
  If no issue covers your change, open one before submitting.
  Use `part of` or `partially answers` in front of the link when the commit is only a step towards
  fixing a broader issue.
  This is for the `CHANGELOG.md`, commit messages should use the "standard" `Fix #N` when the issue
  is close, as understood by github or gitlab.

### Documentation and related files

* Any change to `pdi/include/pdi.h` **must** be mirrored in `mock_pdi/pdi.h`.
* New CMake options, changes to the YAML configuration and changes to the API must be documented in
  `pdi/docs/`.
* Document any new or changed function or class with doxygen.

### Copyright and authorship

Update the copyright header of every file you substantially modify, with your institution and the
current end-year, and add yourself to the `AUTHORS` file.

### Changing the dependencies

Adding a dependency, dropping one or changing the required version of one touches far more than the
build files, so work through this list:

* update `pdi/docs/Source_installation.md`, which is the authoritative list of dependencies and
  supported versions;
* update `spack.yaml`;
* update the distribution `CMakeLists.txt` as well as every `CMakeLists.txt` that actually uses the
  dependency;
* update the dockerfiles used for the tests;
* change `.github/workflows/*.yml` to use the new docker test images;
* prepare the update of the spack, deb and RPM packages for the next release.

If the new minimum compiler versions support a more recent version of C, C++ or Fortran, that is a
language version change as well: update `pdi/docs/Source_installation.md`, the language versions
stated in the [coding style](#coding-style) below, and every `c_std_??` and `cxx_std_??` in the
CMake files.

## Submitting your work

Branch from `main` and open your pull request against it.
Reference the issue your work resolves in the commit message, using a `Fix #issue` keyword where the
change closes it outright.

The pull request template lists the checks to run through before asking for a review; they are the
points covered above, plus the formatting check described in [Running the
tests](#running-the-tests).

## Publishing a release

This concerns the maintainers.
To publish a new release:

* run `bin/release`;
* describe the release at https://github.com/pdidev/pdi/releases;
* publish the new packages at https://github.com/pdidev/pkgs;
* publish the new recipes at https://github.com/pdidev/spack.

## Coding style

### Common C / C++ conventions

Naming:
* macro names *must* be all caps and begin with the `PDI_` prefix
* any public (app or plugin) symbol *must* be exported using the `PDI_EXPORT` macro

Only the public application and plugin API is exported.
`PDI_EXPORT` and `PDI_NO_EXPORT` come from the `pdi/export.h` header generated by CMake's
`generate_export_header`.
Classes declared in `src/` are library-internal and *should* be marked `PDI_NO_EXPORT` so that they
do not become part of the shared library's interface.

Includes *should* be grouped in blocks separated by an empty lines with files in each block ordered
in an alphabetical fashion.
The blocks *should* be in order:
1. in case of an implementation file (cxx) of the PDI library, "config.h"
2. the "mpi.h" file
3. standard C/C++ includes
4. system (POSIX) headers
5. external library dependencies headers
6. PDI dependencies (starting with "pdi/pdi_fwd.h" for header files)
7. in case of an implementation file (cxx), the implemented PDI header

Includes *should* use the bracket notation, except for the headers of the component being compiled
when included from one of its implementation (cxx) files, which *should* use the quote notation.
In practice, an implementation file of the PDI library refers to the library's own headers as
`"pdi/error.h"`, whereas a plugin refers to them as `<pdi/error.h>`.

Header files *must* be protected by an include guard named after the path of the file, in all caps,
with a trailing underscore: for example `PDI_ARRAY_DATATYPE_H_` for
`pdi/include/pdi/array_datatype.h`, and `DECL_HDF5_FILE_OP_H_` for `plugins/decl_hdf5/file_op.h`.

### C coding conventions

These conventions only apply to the C part of PDI (the C public application API).

PDI C public application API is C 17.
Features from more recent versions of C are not allowed.

Naming:
* all public elements (symbol, type, macro, ...) *must* start with the `PDI_` prefix
* for other elements the name *must* be lowercase except for the PDI prefix and *should* be
  constituted of words separated by underscores (snake_case)
* enum names *must* end with a `_e` suffix
* struct names *must* end with a `_s` suffix
* typedefs names *must* end with a `_t` suffix
* function pointer typedefs names *must* end with a `_f` suffix

Prototypes:
* any public or library-wide function *should* return a `PDI_status_t` error status

### C++ coding conventions

PDI is C++ 20.
Features from more recent versions of C++ are not allowed.

The auto keyword should only be used in one of the following cases:
* in iterations, either in a range based for, where it *should* be spelled `auto&&`, or to refer to
  iterators
* to store objects that can not be typed otherwise (e.g. lambdas)
* to store the result of an expression specifically specifying the type of the generated value (e.g.
  a new expression)

Naming:
* class names *must* begin with an upper case letter and use underscore to separate words
* functions and variable names *must* begin with a lower case letter and use underscore to separate
  words
* non-static member variables names *should* begin with an `m_` followed by lower case and
  underscores
* static member variables names *should* begin with an `s_` followed by lower case and underscores
* global variables names *should* begin with an `g_` followed by lower case and underscores

Test code is an exception to these naming rules and follows GoogleTest's conventions instead, see
[Unit tests](#unit-tests).

File organization:
* public plugin enumerations *must* be defined in the `pdi/pdi_fwd.h` header
* public plugin classes and structures *must* be forward-declared in the `pdi/pdi_fwd.h` header
* No implementation should be provided in header files, even `= default` implementations.
  Templates, whose definition the compiler requires at the point of instantiation, are the
  exception.

### Namespaces

All PDI code lives in the `PDI` namespace.

No `using` directive or declaration *must* ever appear at the global scope of a header file: it
would be forced on every file that includes it, directly or not.

In implementation (cxx) files, a module *may* use a `using` directive for its **own** namespace, the
core library may write `using namespace PDI;`, and the Decl'HDF5 plugin
`using namespace decl_hdf5;`.
Apart from that, `using namespace` *should* be avoided; bring in the individual symbols you need
with a `using` declaration instead.
This applies in particular to `std`, which *should* never be pulled in wholesale.
The one further exception is an external library that specifically recommends a directive for its
own namespace, as pybind11 does for `pybind11::literals`.

`PDI::impl` is a private namespace holding implementation details that have to sit in a public
header because they are templates.
It is not part of any API: plugins and applications *must not* refer to anything it contains, and
its contents may change without notice.

Where an implementation can be kept out of the public headers entirely, prefer the pimpl idiom over
`PDI::impl`, a nested `Impl` class marked `PDI_NO_EXPORT` and defined in `src/`, as
`Expression::Impl` does.

A plugin made of several files *should* place its own code in a namespace named after the plugin, at
global scope; `decl_hdf5`, `decl_netcdf` and `set_value` do this.
Single-file plugins *should* use an anonymous namespace instead.

The `std` namespace *must not* be reopened, except to specialise a standard template such as
`std::hash` for a PDI type.

### Unit tests

The C++ unit tests use GoogleTest, whose API is camel case throughout and which forbids underscores
in the two arguments of `TEST`, `TEST_F` and their variants, a suite name with an underscore in it
is rejected by the framework itself.

Test code therefore follows **GoogleTest's naming conventions rather than PDI's**:
* test suite names *must* be camel case without underscores
* test fixture classes *should* be camel case, so that a fixture and the suite it serves can share a
  name
* the helpers of `pdi/include/pdi/testing.h`, which is an extension of GoogleTest rather than part
  of the PDI API, follow the same convention; `PdiTest`, `InitPdi` and `FinalizePdi` are named the
  way GoogleTest would name them

This is a deliberate exception to the C++ naming rules above, limited to test code: `PdiTest` is not
a violation of the class naming rule.
Individual test *case* names, the second argument of `TEST_F`, are commonly snake_case in this code
base and only have to avoid underscores at their start and end, which GoogleTest also rejects.

### Logging

Logging should be done using the spdlog library and exceptions.
The standard C++ `cerr`, `clog` and `cout` should never be used except to diagnose issues that
appear before or after the initialization of spdlog.

The log levels should be used as follow, the first category that applies should be used:
* **fatal error** an invalid situation has been detected by the library (invalid user input, invalid
  hardware behaviour, etc.), the library has no way to recover.
  This is reported by throwing an exception.
* **error** an invalid situation has been detected by the library (invalid user input, invalid
  hardware behaviour, etc.), the library will work-around this, but the user must definitely correct
  this.
* **warning** a very likely invalid situation has been detected by the library (user input that is
  technically valid, but very unusual for example), this is not technically incorrect so the library
  will continue as planned, but the user should definitely be notified.
* **info** a normal situation of the execution is likely useful for the user to understand the
  behaviour of the library after the fact, this should be limited to a few important steps of the
  execution.
  This should not include or require any knowledge about the internal working of the library.
* **debug** a normal situation of the execution might be useful for the user to understand the
  behaviour of the library when specifically looking to diagnose an unexpected behaviour.
  For example, a default value is used because the user didn't provide a specific value for a given
  call.
  This should not include or require any knowledge about the internal working of the library.
* **trace** a normal situation of the execution might be useful for the developers to diagnose the
  behaviour of the library.
  This typically requires knowledge about the internal working of the library to be correctly
  understood.

### Documentation

Public functions and classes are documented with doxygen, using the backslash form of the commands
(`\param`, `\return`, `\brief`, ...) rather than the `@` form.

### Indentation and line length

A `.clang-format` configuration file is provided at the root of PDI distribution, the formatting it
describes should be followed.
It limits source lines to 150 columns.
`./bin/test_indent` checks a working tree against it and `./bin/test_indent --apply` reformats it in
place.

Markdown files are not covered by `.clang-format`.
Their lines *should* be kept to 100 columns unless there is a good reason to exceed it; a line that
cannot be folded without changing what is rendered is such a reason, as in a code block, a long URL
or a table row.

Wrap prose by hand, and *always* break the line at the end of a sentence, so that each sentence
starts on a line of its own.
This keeps diffs limited to the sentences that actually changed.
Break within a sentence only when it would otherwise exceed the 100 column limit, and do not break a
line earlier than that without a reason.
